# 포트폴리오 정리 (AX 직무용)

README는 프로젝트 소개이고, 이 문서는 지원서·이력서·면접에 옮겨 쓰기 위한 정리다. `[ ]`로 표시한 곳은 본인이 확인해 채워야 한다.

## 한 줄 소개

응급 상황에서 LLM 에이전트가 **틀린 정보를 말하지 못하게 하고, 빠르고 싸게 답하게** 만든 응급실 안내 에이전트. (Python · LangGraph · Gemini · Streamlit)

## 내 역할

팀 프로젝트(6인, 모듈별 담당 분리)에서 두 단계로 기여했다.

| 단계 | 내용 |
|---|---|
| **1차 (기존)** | `memory/` 모듈 구현: 사용자 컨텍스트·세션·방문 계획 저장소 (`feat: memory 모듈 추가 #1`). `[담당 범위 확인]` |
| **2차 (v2, 이 브랜치)** | 팀 모듈을 통합해 동작하는 에이전트로 만들고, 안전·성능·검증을 재설계 |

### v2에서 한 일

1. **통합**: 따로 만든 메모리·검색·가드레일·의료 API·화면을 실제 LangGraph 에이전트 하나로 연결했다. 통합 과정에서 드러난 계약 불일치(후보 근거, 승인 재개, 위치 변경 시 이전 후보 처리)를 고쳤다.
2. **안전을 구조로 이동**: 위급 입력의 모델 호출 전 단락, 모델 수치 비채택 + 조회 근거 재구성, 승인 후 1회 저장(거절·중복·위치 변경 시 미저장), 개인정보 마스킹.
3. **지연·비용 최적화**: 도구 호출 순서를 모델이 아니라 서버가 계획(`ServerPlannedCalls`)하도록 바꿔 검색당 메인 모델 호출을 5회 → 1회로 줄였다. P50 약 21초 → 5~8초.
4. **평가 체계**: 위급도 골든셋(75건)과 회귀 감시, 지연·비용 벤치마크(20회 반복, 전/후 비교 CLI), 실제 API 계약을 매일 점검하는 CI.
5. **신뢰할 수 있는 검증 기록**: 오프라인 테스트·실제 API 실측·합성 평가를 구분해 기록하고, 측정하지 못한 것(추천 정확도, 임상 타당성)을 명시했다.
6. **체험 가능성**: API 키 없이 실제 그래프와 가드레일을 돌려 볼 수 있는 데모 모드(`ER_DEMO=1`), 검색 진행 상태 표시, 아키텍처 문서.

## 이력서용 문구

**한 줄**
- 응급실 안내 LLM 에이전트의 안전 가드레일·평가·성능 개선을 맡아, 검색당 모델 호출 5→1회, 응답 지연 약 21초→5~8초(P50)로 개선하고 위급도 분류 재현율을 90%→100%로 높임 (합성 골든셋 75건 기준)

**불릿 (택 3~4)**
- LangGraph 기반 응급실 안내 에이전트에서 도구 호출 순서를 서버가 계획하도록 재설계해 모델 호출 5→1회, P50 지연 약 21→5~8초, 턴당 비용 약 $0.003~0.006 달성 (3시나리오×20회, 60/60 성공)
- 위급 입력은 LLM 호출 전에 119 안내로 단락하고, 모델이 낸 병원·병상 수치는 채택하지 않고 모델 밖에 보관한 API 조회 결과로 답변을 재구성해 환각 경로를 구조적으로 차단
- 합성 골든셋 75건으로 위급도 분류를 평가: 정확도 85.9%→96.9%, 위급 재현율 90%→100%, 오차단 0건. 데이터 과적합 가능성과 임상 미검증을 문서에 명시
- 오프라인 테스트 426개(소켓 차단 환경), `mypy --strict`, 일 단위 실제 API 계약 CI를 구성하고 측정 가능한 항목과 불가능한 항목을 분리해 기록
- 사람 승인(HITL) 후에만 방문 계획을 1회 저장하는 LangGraph interrupt/resume 흐름 구현

## AX 직무 관점에서 강조할 점

AX(업무·서비스의 AI 전환)에서는 "모델을 붙였다"보다 **업무에 안전하게 넣고, 효과를 숫자로 보이고, 운영할 수 있게 만든 경험**이 평가된다. 이 프로젝트는 각각에 답이 있다.

| AX에서 묻는 것 | 이 프로젝트의 답 |
|---|---|
| 어디에 AI를 쓰고 어디엔 쓰지 않는가 | 고정된 검색 단계는 서버 코드, 문장 작성만 LLM. 위급 판단 1차는 규칙 |
| 위험을 어떻게 통제하는가 | 입력 가드 · 출력 근거 재구성 · 승인 게이트를 코드로 구현 (프롬프트 의존 아님) |
| 효과를 어떻게 증명하는가 | 전/후 벤치마크 JSON, 골든셋 지표, 재현 명령 |
| 비용·지연은 | 호출 횟수·토큰·턴당 비용을 측정하고 모델 계층화(분류기는 경량 모델) |
| 운영·유지보수 | 계약 테스트 CI, 오류 분류(실패 vs 빈 응답), 캐시 상태 표시 |
| 한계를 아는가 | 임상 검증 없음·합성 데이터·단일 지역 측정을 문서 최상단에 기록 |

## 면접 예상 질문과 답변 뼈대

- **왜 도구 순서를 서버가 정했나?** 응급 검색은 단계가 고정이라 모델의 판단이 가치를 더하지 못하고 지연·비용·변동성만 늘렸다. 그래서 계획은 코드, 작문은 모델로 분리했다. 대신 예외 상황(결과 없음, 반경 확대)은 planner가 처리하며 `[이 부분 설명 준비]`.
- **지연 개선 효과가 모델 교체 때문 아닌가?** 맞다. 모델 교체와 서버 계획이 섞여 있어 분리하지 못했다고 문서에 적었다. 분리하려면 같은 모델로 계획 방식만 바꿔 재측정해야 한다(다음 단계).
- **골든셋 96.9%를 믿을 수 있나?** 아니다. 놓친 문장을 보고 규칙을 보강했으므로 낙관적이다. 일반화는 새로 작성한 사례로 다시 재야 하고, 임상 타당성은 의료진 검토 없이 주장하지 않는다.
- **LLM 분류기가 등급을 올리기만 하는 이유?** 위급 상황에서 과소 분류가 과대 분류보다 훨씬 위험하다. 실측에서 과대 분류가 1건 늘었지만 과소 분류는 늘지 않았다.
- **개인정보는?** 위치·증상은 서버 메모리에만 두고 영구 저장하지 않는다. 주소는 동의 후 저장, 전체 삭제 기능 제공. 영구 저장은 보관 정책을 먼저 정해야 해서 하지 않았다.
- **다음에 한다면?** 같은 모델로 계획 방식만 바꾼 분리 실험, 새 사례 기반 골든셋 확장과 의료진 검토, 다지역 측정, 영구 저장소 교체.
