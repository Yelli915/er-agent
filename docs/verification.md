# 검증

계약과 설계는 [design.md](design.md)에 정리되어 있다. 이 문서는 수행한 검증의 기록, 앞으로 검증할 항목과 판정 기준, 지연과 비용의 측정 절차를 다룬다. 계획표에서 결과 열이 비어 있는 항목은 아직 측정하지 않은 것이다.

## 1. 실행 기록

기준은 upstream `main`의 `00971aa` 이후 통합 수정이다.

### 1.1 수정 범위

- 실제 `ERFinderContext`, `ERFinderStore`, `SessionManager`, `VisitPlanService`를 연결했다.
- LangGraph 메시지 입력, interrupt와 resume, 서버의 도구 순서 및 후보 근거 검증을 적용했다.
- 사용자가 선택한 병원만 승인 후 한 번 저장한다. 거절, 중복 승인, 위치 변경, 이전 후보는 저장하지 않는다.
- 기관 주소에서 시도와 시군구를 얻고, KST 시각, `MKioskTy` 값, 비정상 숫자를 처리한다.
- API 실패와 정상적인 빈 응답을 구분하고, 조회가 실패하면 추가 호출을 중단한다. 캐시 사용과 강제 갱신은 화면에 표시한다.
- 개인정보 마스킹과 입력 범위 검사를 수행하고, 위급 규칙에 해당하면 모델을 호출하기 전에 안내한다.
- 방문 기록은 최신 페이지를 조회하며 체크포인트는 엄격하게 역직렬화한다.
- 좌표를 직접 입력할 수 있으며, 로컬 실행기는 프로젝트 `.env`를 우선 적용한다.

### 1.2 실제 API 확인

2026-09-11에 로컬 키로 실행했다. 공개된 강남역 좌표와 저장소에 있는 합성 증상만 사용했으며, 사용자의 실제 위치나 건강정보는 수집하지 않았다. 카카오 API는 호출하지 않았다.

| 흐름 | 결과 |
|---|---|
| 일반 검색 (`live-full-flow.json`) | OpenAI와 E-Gen 실제 호출이 성공했다. 반경 5km 안의 기관 3곳에서 병상, 전화, 주소를 확인했다. 검색에 약 21초, 메인 모델 호출 5회가 소요되었다. |
| 선택, 거절, 재선택, 승인, 중복 승인 | 저장 횟수는 차례로 0회, 0회, 1회, 추가 없음이었다. 승인과 거절을 포함한 전체 확인에 약 36.8초가 걸렸다. |
| 중증 검색 (`live-urgent-flow.json`) | 수용 가능(`yes`)으로 확인된 기관 2곳을 반환했다. 검색에 약 14.8초(연결과 정리를 포함하면 약 16.8초), 메인 모델 호출 5회가 소요되었다. |

위 수치는 단일 실행의 실측값이므로 일반적인 성능을 보장하지 않는다. 합성 입력에 대한 응급도 판단이나 추천의 임상적 적절성을 검증한 결과도 아니다.

### 1.3 오프라인 회귀

`python scripts/verify.py --scope all`을 Windows와 Python 3.14에서 실행한 결과(2026-10-18) 360개 테스트가 모두 통과했고 실패, 오류, 건너뜀은 없었다. Ruff와 `git diff --check`도 통과했다. 실행 근거는 `verification-results/`의 `report.json`, `junit.xml`, `pytest.log`에 저장된다.

오프라인 검증은 실제 메모리, 검색, LangGraph를 실행하고 녹화된 API 응답을 사용한다. 외부 소켓 통신은 차단하되, Windows의 asyncio가 동작하도록 같은 프로세스 안의 loopback 연결만 허용한다. 리스너가 닫히거나 해제되면 해당 포트는 더 이상 허용하지 않는다. Windows에서 `pytest`를 직접 실행할 때는 `PYTHONUTF8=1`을 설정해야 한다.

`integration.status`가 `NOT_VERIFIED`인 것은 오프라인 명령만으로는 실제 API 연동과 임상 검증의 통과를 선언하지 않는다는 의미다. 테스트 수집 오류가 남아 있으면 일부 테스트가 통과하더라도 전체 결과는 FAIL이며, 정적 검사만으로 통합 통과를 판정하지 않는다. 오프라인 테스트의 결과와 실제 API 및 LLM 실행 결과는 별도의 증거로 기록하고, pytest 실행 시간을 추천 지연 시간으로 사용하지 않는다.

### 1.4 로컬 검토와 보조 수단

로컬 검토는 `python scripts/run_local.py`로 서버를 띄우고 http://localhost:8503 에서 진행한다. 왼쪽의 주소 검색 없이 좌표로 조회하는 옵션을 선택하고, 에이전트 연결을 확인한 뒤 에이전트 상담 탭에서 증상을 입력한다. `.env`는 Git에서 제외되며 키는 화면, 로그, 문서에 기록하지 않는다.

| 수단 | 명령 | 용도 |
|---|---|---|
| 위급도 골든셋 | `python scripts/eval_golden.py [--live]` | 과소 분류, 과대 분류, 차단 누락을 측정한다 (`tests/fixtures/golden/triage.json`). |
| 실제 API 계약 점검 | `ER_RUN_LIVE=1 pytest tests/live -m live` | E-Gen과 OpenAI의 응답 형식 변경을 감지한다. `live-contract.yml`이 매일 실행한다. |
| 지연·비용 벤치마크 | `python scripts/benchmark.py --live` | 4절에서 설명한다. |

### 2.4 알려진 한계

- E-Gen 병상 정보는 병원이 직접 입력하므로 실제 상황과 다를 수 있으며, 방문 전에 전화로 확인해야 한다.
- 병상 조회가 시도와 시군구 단위로 이루어져, 경계 지역에서는 반경 안의 기관이 조회 대상에서 빠질 수 있다.
- 검증 데이터는 서울과 강원 지역에서 녹화한 것으로 한정되며, 추천 정확도는 측정하지 않았다.
- 위급도 분류는 규칙 사전과 분류 모델에 의존하므로 드문 표현은 한 단계 낮게 분류될 수 있다. `confidence`가 0.6 미만이면 한 단계 올려 보정한다.
- 공공 API의 응답 지연은 서비스 상태에 따라 달라지며, 측정값은 실행 시점의 값이다.

## 4. 벤치마크 절차

"메인 모델 호출 5회에서 N회로 감소"와 같은 개선 주장은 동일한 조건에서 반복 측정한 값(P50, P90, 표본 수, 턴당 비용)으로 뒷받침한다. 현재 저장소에 있는 실측은 1.2절의 단일 실행 2건뿐이다.

### 4.1 측정 원칙

- 모델명, `reasoning_effort`, 타임아웃, 시나리오, 좌표를 결과 JSON에 함께 기록한다.
- 보고서의 숫자는 회차별 원본에서 계산하며 손으로 옮기지 않는다.
- 지연은 검색 처리 시간과 연결·정리를 포함한 전체 시간으로 구분한다.
- 표본 수와 실패율을 항상 함께 적고, 실패한 회차를 제외하지 않는다.
- 지연과 비용만 다루며 임상적 주장은 하지 않는다.
- 키, 입력 원문, 모델 출력 원문은 JSON에 남기지 않는다.
- 합성 증상과 공개 좌표(강남역)만 사용한다.
- 개선 전후 측정은 같은 날 번갈아 실행해 외부 API의 변동을 줄인다.

### 4.2 시나리오와 명령

시나리오는 일반(standard), 중증(urgent 또는 critical이면서 질환 조건 포함), 같은 지역 재질의의 세 가지이며 `benchmark.SCENARIOS`에 정의되어 있다. 매 회 새 세션으로 실행하고, 재질의 시나리오만 앞선 턴을 먼저 실행한다. 앞선 턴의 비용도 `--budget-usd`에 합산한다.

```bash
python scripts/benchmark.py --live --no-server-planned --label baseline --prices <단가> --output docs/benchmarks/baseline.json
python scripts/benchmark.py --live --label after --prices <단가> --output docs/benchmarks/after.json
python scripts/benchmark.py --check docs/benchmarks/after.json
python scripts/benchmark.py --compare docs/benchmarks/baseline.json docs/benchmarks/after.json
```

`--live` 옵션이 없으면 실행하지 않으며, `--budget-usd`를 쓰려면 `--prices`가 필요하다. 결과 JSON은 `docs/benchmarks/`에 보관하고, 커밋하기 전에 `--check`로 비밀값과 필수 항목을 점검한다. 턴당 비용은 메인 모델과 분류기 각각의 입력·출력 토큰에 단가를 곱해 더한 값이며, 단가는 실행 시점의 가격표를 기준으로 한다. 먼저 표본 3회로 비용을 추정한 뒤 허용 비용 안에서 표본 수(기본 20)를 정한다.

| 기준선과 개선 후 실측 | 미실행 | 실제 키로 위 명령을 실행해야 한다 |
| 지연 벤치마크의 주기 실행 | 미구현 | 계약 점검(`live-contract.yml`)만 있다 |

지연과 비용의 개선 폭은 실측을 실행해야 확인할 수 있다. 실측이 끝나면 `--compare`의 출력으로 비교표를 작성하고 1절과 3절의 빈 항목을 갱신한다. 결과는 "지연 N초에서 M초로 감소 (n=…, P50/P90)"와 같이 조건을 함께 적는다.

주요 위험과 대응은 다음과 같다. 외부 API의 편차는 교차 실행과 분산 표기로 줄인다. 안전 규약이 약해지는 일을 막기 위해 변경할 때마다 `verify.py --scope all`을 실행한다. 비용 초과는 `--budget-usd`로, 키 노출은 secret 사용과 `--check`로 방지한다.
